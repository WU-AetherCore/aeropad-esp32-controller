# 控制数据协议 v1

> 接入设备先读 [接收端教程](RECEIVER_INTEGRATION.md)。本文件是线格式规范，控制映射与驱动接口由目标端提供。

## 适用范围与参考程序

仅“蓝牙模块控制”使用本协议。遥控器作为BLE客户端写对方NUS/FFE0特征，模块经UART透传给目标MCU，目标程序负责解码、映射与失联停止。HID报告、原作者NRF结构体和WiFi网页数据不属于本协议。

四格式解析器：[host_receiver.py](../examples/host_receiver.py)；可移植二进制解析器：[ControlReceiver.h](../examples/common/ControlReceiver.h)。[12组机读测试向量](protocol_vectors.json) 由 [发送端编码生成器](../tools/export_protocol_vectors.cpp) 导出，含线上字节HEX和期望字段，覆盖静止、正负轴/按键、释放。

本协议是本派生工程新增协议，不保证兼容原作者接收端。实际编码以 `src/ControlPacket.h` 为准；本地测试为 `tools/test_control_packet.cpp`。

## 四种发送格式

入口：蓝牙中心 → 发送设置，或蓝牙模块控制 → 模块设置 → 发送设置。上下选择格式/间隔，左右改变，X返回。设置立即写入NVS，旧版JSON开关自动迁移为格式0或1。

|编号/名称|线上内容|单帧长度（含换行，不含C字符串末尾NUL）|建议接收方式|
|---|---|---|---|
|0 二进制|20个原始字节|固定20字节|串口助手勾选HEX接收，程序按同步头+CRC解析|
|1 JSON文本|UTF-8兼容ASCII JSON对象，以LF结束|96～127字节，随数字位数变化|文本接收，按换行拼接后解析JSON|
|2 HEX十六进制|二进制帧的20个字节转为大写ASCII HEX，空格分隔，以LF结束|固定60字节：40个HEX字符+19个空格+1个LF|文本接收看到`A5 5A ...`；HEX接收会显示这些ASCII字符的编码|
|3 文本数据|`AP1`开头的带字段名ASCII，以LF结束|64～90字节，随数字位数变化|文本接收，按换行分帧，再拆`key=value`|

HEX是“字节值的文本表示”，与原始二进制是不同的线上格式。文本与JSON不含CRC；需CRC时使用二进制或HEX。编码缓冲区192字节，错误/容量不足返回0，不发送半个逻辑帧。

## 帧头、帧尾与完整一行显示

|格式|帧头/起始识别|结束识别|数据保护|
|---|---|---|---|
|二进制|`A5 5A 01 01`|从同步头起固定 20 字节，最后两字节是 CRC；没有独立帧尾|CRC16 校验、版本/保留位/字段范围检查|
|HEX|行首 `A5 5A 01 01` 的 ASCII 字符|LF，字节 `0A`；换行前恰好 20 个 HEX 字节词|转回 20 字节后执行同样的 CRC 检查|
|文本|`AP1 `|LF，字节 `0A`|完整字段、范围、重复字段检查；没有 CRC|
|JSON|`{`，且对象中的 `v` 必须为 1|LF，字节 `0A`；完整 JSON 对象|JSON 语法、字段类型/范围检查；没有 CRC|

**不要把 CRC 当作固定帧尾，也不要看到 `5A` 就结束。** 二进制载荷和 CRC 可以包含任意字节，包括 `0A`、`A5`、`5A`。需要校验的数据控制建议选择二进制；需要肉眼查看且保留 CRC，选择 HEX。文本与 JSON 是便于调试的表示，不能宣称有 CRC、身份认证或执行确认。

### 照片里为什么分成四行

例如这是一条完整文本帧（最后还有 LF）：

```text
AP1 seq=86 LX=0 LY=0 RX=0 RY=0 KL=-88 KR=-74 BTN=00000 AX=40 AY=2 N=0
```

BLE 默认 MTU 23 时，每次 GATT 写最多 20 字节。模块把这些片段分次送到 UART，串口助手若勾选“加时间戳和分包显示”，会在每批收到的字节前添加时间并另起一行；这些时间和“收←”不是遥控器协议内容。分包可以发生在 `KR=-74` 的中间，接收端不能把每次串口读取当作完整数据。

SSCOM 文本查看：关闭“HEX显示”、取消“加时间戳和分包显示”，按发送端 LF 换行显示。不要靠把分包超时调大来定义协议帧，它会受无线延迟影响。若要严格每帧一行，先关闭占用 COM12 的串口助手，再运行：

```powershell
& "$env:USERPROFILE/.platformio/penv/Scripts/python.exe" examples/host_receiver.py --port COM12 --baud 115200 --format text --display line
```

该工具先累积片段，收到 LF 后校验并输出一整行；半帧不输出，非法帧不输出。二进制选择 `--format binary`，同样支持 `--display line`，但显示的是解码后的字段，不是二进制线上字节。程序只读取并展示，不发送运动指令。

### 接收端必须做到的保护

1. 累积输入，允许任意分片和多帧粘连。二进制查同步头、收满 20 字节并检查 CRC；失败时移动一个字节重新找头。文本/JSON/HEX 等到 LF，行长超过 191 字节时丢弃到下一个 LF。
2. 校验版本、字段范围及保留位，通过后才更新控制值。断线或切换格式清除未完成帧。按键位图不能按字符串位置猜测。
3. 使用本地单调时钟的“最近有效帧”超时停车；CRC 错误、垃圾数据或重复序号不能维持旧运动。参考接收程序默认 300ms，发送推荐 20/50ms；2 秒发送间隔不能直接配 300ms 控制超时。
4. `N=1` 表示释放，轴和按钮清零，但它不是停车确认。接收端仍须独立失联保护；要确认真实停止，需要目标端提供新鲜状态反馈。
5. 本协议没有认证、重传 ACK 或防重放加密层。BLE 写成功只说明提交了数据；不能将其当作电机停止或动作完成。

## 模拟量与状态字段

|JSON字段|文本字段|含义|类型/范围|
|---|---|---|---|
|v|`AP1`中的1|协议版本|整数1|
|seq|seq|帧序号，含释放帧，每发送一帧加1，255后回0|uint8，0～255|
|lx、ly|LX、LY|左摇杆水平/垂直输出|有符号整数，-100～100，校准中心/死区内为0|
|rx、ry|RX、RY|右摇杆水平/垂直输出|同上|
|kl、kr|KL、KR|左、右两个ADC旋钮的归一化输出|同上；不是0～4095原始ADC|
|buttons|BTN|18路按键/拨杆位图|uint32有效低18位；JSON十进制，文本固定5位大写HEX|
|ax、ay|AX、AY|MPU6050的X/Y倾角归一化控制量|有符号-100～100；±45°映射±100，超过截断；不是角度单位，也不是立方体三轴显示值|
|neutral|N|释放/停止标志|0正常；1时所有轴、旋钮、按键及AX/AY清零|

轴方向取当前引脚及校准映射，不在协议层猜测无人机/车辆油门正负。接收端应自行定义油门、转向、俯仰等用途。原始按键电平低表示按下，协议已转换为 **bit=1表示按下/拨杆有效**。

代码中LX/LY的ADC相对中心增加为正，RX/RY取反；两旋钮的校准最小ADC映射100、最大ADC映射-100。实物方向取决于安装与接线，接收端须观察正负后再决定控制符号。旋钮不操作不意味着输出0；后面的零值例子假设两旋钮也在中点。

## 二进制布局：20字节

多字节字段小端；六轴和AX/AY是int8的二进制补码，例如-100=0x9C、100=0x64。接收时用int8_t解释，不能当uint8_t显示为156。

|偏移|字节数|类型|内容|
|---|---|---|---|
|0|1|uint8|同步头A5|
|1|1|uint8|同步头5A|
|2|1|uint8|版本01|
|3|1|uint8|帧类型01（控制）|
|4|1|uint8|seq|
|5、6|各1|int8|LX、LY|
|7、8|各1|int8|RX、RY|
|9、10|各1|int8|KL、KR|
|11～13|3|uint24 LE|按键位图，bit18～23保留0|
|14、15|各1|int8|AX、AY|
|16|1|uint8|bit0=neutral，其他位保留0|
|17|1|uint8|保留0|
|18～19|2|uint16 LE|CRC，低字节在18，高字节在19|

CRC16-CCITT-FALSE：多项式0x1021，初始0xFFFF，RefIn/RefOut=false，XorOut=0；仅覆盖偏移0～17这18字节。标准向量ASCII `123456789`的CRC=0x29B1。

## BLE分片与UART

正常静止帧的JSON与文本例子（序号0，所有按键松开）：

```json
{"v":1,"seq":0,"lx":0,"ly":0,"rx":0,"ry":0,"kl":0,"kr":0,"buttons":0,"ax":0,"ay":0,"neutral":0}
```

```text
AP1 seq=0 LX=0 LY=0 RX=0 RY=0 KL=0 KR=0 BTN=00000 AX=0 AY=0 N=0
```

线上每行末尾均含一个`0A`（LF）。若左摇杆X=50、右摇杆Y=-20且按A，分别变为`lx:50`/`LX=50`、`ry:-20`/`RY=-20`、`buttons:1`/`BTN=00001`。接收程序不能把BTN的HEX字符串直接当十进制。

支持NUS服务`6e400001-b5a3-f393-e0a9-e50e24dcca9e`（写0002/通知0003）和FFE0/FFE1。默认 MTU23 时每次写最多20字节。通用 FFE0 透传模块保守限制每片20字节、相邻片间隔20ms，支持时使用 Write Command；其他服务按协商MTU、最多180字节分片。车辆自定义协议页另行保留其确认写入与反馈保护策略。**一次GATT写入不等于一帧**。接收端按20字节+CRC复原二进制，ASCII格式按LF复原；忽略空行，限制行长，断线时清除半帧。

发送间隔可选20、50、100、200、250、500、1000、1500、2000ms，分别约50、20、10、5、4、2、1、0.67、0.5帧/秒。它是调度间隔，不保证无线拥塞时严格频率。退出控制/断开时尝试发送neutral，接收端仍需独立失联处理。

seq仅用于顺序/重复诊断，不是执行ACK或认证。丢帧后可以出现跳号，255→0正常回绕；不要强制每包必须加1。重复seq不应维持旧运动，非法包不刷新有效帧看门狗。原始二进制没有换行；ASCII三格式以LF分帧，断线/切换格式清理半帧与状态。

8N1串口每字节约10bit。例如最长JSON127字节在20ms发送约6350字节/秒，115200bps通常有带宽空间，9600bps的约960字节/秒则不够；应提高UART速度、增加间隔或改二进制。2秒间隔适合慢速状态传输，不适合需要快速响应的运动控制。

BLE-UART桥接示例的5000ms是BLE写入静默检测，以容纳2000ms设置，任意片段可刷新它；它不验证控制包，不是执行器有效帧看门狗。新增UART控制示例使用300ms有效帧超时，建议20/50ms发送。目标端应定义自己的超时和停止动作；TX写成功不是设备动作成功。

## 串口设置及回显

串口设置位于蓝牙模块控制内：未连接页面按B打开模块设置，选择串口设置按O；连接后设备操作菜单选择串口设置。进入后上下选择本机/对方，本机左右切换关闭、原始二进制、HEX、文本、JSON五种回显选项，对方按O进入远程参数页，X逐级返回。

原始二进制直接输出收到的通知字节，不加前缀或换行；HEX把同一批字节转为可读十六进制。例如收到ASCII `AT`：原始模式输出字节`41 54`，HEX显示字符`41 54`，文本预览显示`AT`。发送格式和接收回显格式是独立设置，不会把远端发来的任意数据自动转换成控制协议帧。

COM11是本机USB CDC，关闭、原始二进制、HEX、文本、JSON是五种独立回显模式，不是电气UART波特率。本机接收通知排入512字节缓冲并在UI主循环输出，溢出明确报告丢弃字节；文本模式将非ASCII字节转成`\xNN`，JSON模式输出`len`、连续大写`hex`和转义后的`text`字段。USB回显不等于对方UART参数已正确。

远程波特率需要对方提供NUS扩展特征`6e400004-b5a3-f393-e0a9-e50e24dcca9e`：Read/Write，4字节小端实际波特率。支持9600/19200/38400/57600/115200，写后读回相同才显示已生效。WUFUDONG实际提供FFE0，未提供此扩展，因此当前显示不支持远程设置；设备名称不能确定芯片型号或AT配置命令，不盲发AT指令。

## 蓝牙HID与本协议的区别

“蓝牙游戏手柄”发送标准HID（6个16位轴、14按钮和方向帽），不使用本协议的20字节帧，也不受模块发送格式/间隔设置影响。本协议专用于“蓝牙模块控制”。TX表示完整逻辑帧已提交BLE写入，RX表示通知字节数，ERR表示BLE写入失败；都不是外部设备执行确认。

## 2026-10-09 实际模块联调

遥控器 COM11 编译烧录并校验 Flash，连接 WUFUDONG FFE0 模块，由 CH340 COM12 以 115200、8N1 实际接收。每种格式采样约4秒，发送间隔1000ms：文本350字节/5帧、二进制80字节/4帧、JSON412字节/4帧、HEX240字节/4帧；解析错误均为0，二进制及HEX逐帧CRC验证通过。测试结束恢复文本格式和1000ms间隔，退出控制并关闭连接。原始记录保存在本地 logs/module_wire_test，不发布设备地址。

本次修复通用模块误用周期确认写入的问题，并将需要车辆零速反馈的停车确认限定在车辆协议页。该短时测试验证通用协议字节传输与解析，不代表对方执行器已完成动作，也不是长期无线稳定性或最大吞吐量验收。
